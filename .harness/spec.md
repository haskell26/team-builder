# Team Builder

## This Iteration

이번 실행은 기존 후보 조합 기능을 다듬는 5차 개발이다.
기존 입력/팀 분배/후보 조합/선호도 점수/저장 플레이어 기능은 유지한다.
후보 조합은 같은 역할군 간 밸런스도 맞아야 하며, 특히 탱커 밸런스를 더 중요하게 본다.
이번 우선순위는 현재 10명 확인 영역의 조밀한 한 줄 요약, 추천 후보 6개 재생성 UX, 문의 안내 추가이다.
이번 실행에서는 현재 10명 확인 및 선호 점수 영역도 저장된 플레이어 목록처럼 세로 길이가 과하게 늘어나지 않도록 한 줄 중심으로 압축해 보여 주어야 한다.
추천 팀 결과 영역에는 같은 입력을 유지한 채 후보 6개를 빠르게 다시 생성할 수 있는 버튼이 있어야 한다.
문의 및 건의사항은 GitHub issue 로 올려 달라는 안내를 메인 UI 에 자연스럽게 포함해야 한다.
기존 QA에서 남은 브라우저/모바일 실기기 검증 미완료는 이번 라운드에서 blocker로 간주하지 않는다.
점수는 내부 계산용으로만 유지하고, 메인 UI 에서는 전반적으로 숫자 점수 표기를 하지 않는다.

## Goal

각기 다른 실력을 가진 게임 플레이어 10명이 모였을 때, 밸런스가 맞는 두 팀으로 나누기

## Users

- Who is the primary user?
오버워치 게임 커뮤니티의 관리자
- What problem are they solving?
커뮤니티 내 정해진 플레이어 10명을 밸런스한 두 팀으로 나눠야 한다.

## Core Flows

유저가 데이터를 다음 형식으로 엑셀로부터 복사해와서 붙여넣는다.
|유저 이름|탱커 티어|딜러 티어|힐러 티어|
|...|
그러면 각 티어별로 점수를 할당해서 점수의 총합이 양팀이 가장 적게 차이가 나야 한다. 각 팀은 탱커 1명, 딜러 2명, 힐러 2명으로 구성된다. (Unranked는 양팀에 최대한 비슷하게 분배돼야 한다.)
U 0점 (Unranked)
브론즈 1점
...
다이아 5점
마스터 6점
그마 7점
github.io로 올릴 수 있게 프론트엔드만으로 구성된 프로젝트여야 한다.

## Must-Have Features

- user friendly input (copy-paste from excel)
- nicely-readable output
- product language in korean
- 가능한 후보 조합 6개 생성
- 후보 조합 6개를 한눈에 빠르게 비교할 수 있는 compact preview UI 제공
- 각 후보 preview 에서 팀 A / 팀 B 구성과 역할 배치를 작은 카드 형태로 보여주기
- 플레이어 티어는 이름 또는 이름 배경색으로 직관적으로 표현
- 티어 색상 규칙:
  - 언랭: white
  - 브론즈: bronze
  - 실버: silver
  - 골드: gold (yellow)
  - 플래티넘: mint
  - 다이아: blue
  - 마스터: green
  - 그랜드마스터: violet
- 후보 조합은 다음 우선순위로 정렬:
  1. 총점 차이 최소
  1-1. 총점 차이가 같으면 역할군별 점수 차이 합이 더 작은 후보를 우선한다.
  1-2. 역할군별 점수 차이 합도 같으면 탱커 점수 차이가 더 작은 후보를 우선한다.
  2. 언랭 분배 차이 최소
  3. 1, 1-1, 1-2, 2가 모두 같으면 랜덤하게 정렬
- 사용자가 후보를 선택하면 해당 후보를 최종 편집 영역으로 불러와야 한다.
- 최종 편집 영역에서는 사용자가 플레이어를 직접 클릭해서 서로 스왑할 수 있어야 한다.
- 스왑은 두 슬롯을 차례대로 클릭하면 수행된다.
- 스왑 이후 화면은 즉시 갱신되어야 한다.
- 점수는 내부 계산에만 사용하고, 메인 UI 에서는 개인 점수 / 팀 총점 / 숫자 점수 차이를 기본적으로 표시하지 않는다.
- 플레이어별 역할 선호도는 순위 방식이 아니라 `총 6점` 을 탱커 / 딜러 / 힐러에 분배하는 방식이어야 한다.
- 역할 선호도 기본값은 `탱커 2점 / 딜러 2점 / 힐러 2점` 이다.
- 역할 선호도 점수는 정수로 입력하거나 조정할 수 있어야 하며, 세 역할 점수 합은 항상 6이어야 한다.
- 역할 선호도는 티어 밸런스를 뒤집는 hard constraint 가 아니라 soft signal 이다. 즉, 더 선호도가 높아도 티어 밸런스가 더 나쁜 후보를 우선하지 않는다.
- 후보 계산과 최종 편집은 역할 선호도 점수 정보를 반영할 수 있어야 한다.
- 플레이어 티어 정보를 저장할 수 있어야 한다.
- 저장된 플레이어 목록에서 이번 매치에 사용할 10명을 선택해서 불러올 수 있어야 한다.
- 저장된 플레이어 목록 UI 는 상세 카드보다 이름 위주의 단순한 리스트여야 한다.
- 저장된 플레이어를 삭제할 수 있어야 하며, 전체 삭제 버튼도 제공해야 한다.
- 저장된 플레이어 불러오기 영역은 메인 입력 영역과 세로로 길게 이어지지 않도록 옆 영역으로 분리해야 한다.
- 저장된 플레이어 불러오기 영역은 접기/펼치기 기능이 있어야 하며, 기본 상태는 접힘이어야 한다.
- 저장된 플레이어 한 명의 정보는 한 줄에 표시되어 아래로 과하게 길어지지 않아야 한다.
- 저장된 플레이어 행의 텍스트, 빈 공간, 배경 등 칸 어디를 클릭해도 선택/해제가 가능해야 한다.
- 현재 10명 확인 및 선호 점수 영역도 플레이어 한 명당 한 줄 형태로 압축해서 보여 주어야 하며, 이름 / 티어 / 선호 점수를 한눈에 빠르게 비교할 수 있어야 한다.
- 현재 10명 확인 및 선호 점수 영역은 상하 간격을 줄여 세로로 과하게 길어지지 않게 해야 한다.
- 추천 팀 결과 영역에는 현재 입력과 선호 점수 상태를 유지한 채 후보 조합 6개를 다시 랜덤 생성하는 버튼이 있어야 한다.
- 후보 재생성 버튼은 빠른 탐색용 기능이므로, 기존 입력값이나 저장된 플레이어 선택 상태를 지우지 않아야 한다.
- 메인 UI 어딘가에 문의 및 건의사항은 `https://github.com/haskell26/team-builder/issues` 에 issue 로 올려 달라는 안내가 보여야 한다.
- 입력 헤더 행은 optional 이다. 있어도 되고 없어도 된다.

## Interaction Rules

- 후보 preview 는 빠르게 비교하는 용도이므로 작은 카드/요약 형태여야 한다.
- 최종 편집 영역은 선택된 후보 1개만 대상으로 한다.
- 사용자가 첫 번째 슬롯을 클릭하면 선택 상태가 표시되고, 두 번째 슬롯을 클릭하면 두 슬롯의 플레이어가 서로 교체된다.
- 스왑은 역할 슬롯 기준으로 이루어진다. 즉, 플레이어가 슬롯을 교체하면 해당 슬롯의 역할을 따른다.
- 점수 숫자는 메인 UI 에서 숨기되, 내부 계산과 후보 정렬 로직은 유지한다.
- 역할 선호도 입력은 각 플레이어별 `탱커 / 딜러 / 힐러` 점수 합이 6이 되도록 제한한다.
- 저장된 플레이어 목록은 빠르게 훑고 선택하기 쉬운 이름 중심 리스트여야 한다.
- 저장된 플레이어 영역은 기본적으로 접혀 있어야 하고, 사용자가 필요할 때만 펼쳐서 사용한다.
- 저장된 플레이어 한 줄에는 이름, 핵심 티어/선호도 정보, 선택 상태 정도만 압축해서 보여 준다.
- 저장된 플레이어 선택은 작은 체크박스만 누르는 방식이 아니라, 한 줄 전체를 클릭 가능한 hit area 로 제공한다.
- 현재 10명 확인 및 선호 점수 영역도 플레이어별 카드를 세로로 길게 쌓기보다, 각 플레이어 정보를 한 줄 요약으로 배치해 빠르게 훑을 수 있어야 한다.
- 후보 재생성 버튼은 추천 팀 결과 섹션 안에서 쉽게 보이는 위치에 있어야 하며, 클릭 즉시 새로운 후보 6개를 계산해서 갱신해야 한다.
- 문의 및 건의사항 안내는 숨겨진 개발자용 문구가 아니라 실제 사용자가 찾기 쉬운 텍스트 링크 형태여야 한다.

## Nice-To-Have Features

- 현재는 오버워치만 다루지만 추후 리그오브레전드로 확장될 가능성 있음

## Technical Constraints

- Preferred language or framework: frontend
- Required integrations
- Deployment assumptions: github.io로 프론트엔드만 배포 예정
- Anything the agent must avoid: 복잡한 UX
- 헤더 행은 있을 수도 있고 없을 수도 있다. 둘 다 지원해야 한다.

## Acceptance Tests

- 같은 10명 입력에 대해 후보 조합 6개가 표시된다.
- 후보 조합 6개 preview 가 compact 한 형태로 표시된다.
- 모든 후보 조합은 각 팀이 1탱 2딜 2힐 구성을 만족한다.
- 모든 후보 조합에서 같은 플레이어가 중복 배정되지 않는다.
- 후보 목록은 점수 차이, 언랭 분배 차이 기준으로 정렬된다.
- 총점 차이가 같은 후보들 사이에서는 역할군별 점수 차이 합이 더 작은 후보가 먼저 표시된다.
- 그 조건도 같으면 탱커 점수 차이가 더 작은 후보가 먼저 표시된다.
- 언랭/브론즈/실버/골드/플래티넘/다이아/마스터/그랜드마스터가 지정한 배경색 규칙으로 구분된다.
- 사용자가 후보 1개를 선택하면 최종 편집 영역에 해당 후보가 로드된다.
- 사용자가 두 슬롯을 클릭하면 두 플레이어가 서로 스왑된다.
- 스왑 직후 화면이 즉시 갱신된다.
- 메인 UI 에서는 숫자 점수가 기본적으로 표시되지 않는다.
- 사용자가 플레이어별 역할 선호도 점수를 입력하거나 수정할 수 있다.
- 각 플레이어의 역할 선호도 점수 합은 항상 6으로 유지된다.
- 기본 역할 선호도 값은 `2 / 2 / 2` 이다.
- 역할 선호도 정보가 티어 밸런스를 해치지 않는 범위에서 후보 계산 또는 최종 팀 구성에 반영된다.
- 플레이어 티어 정보를 저장할 수 있다.
- 저장된 플레이어 목록이 이름 중심의 단순 리스트로 표시된다.
- 저장된 플레이어 목록에서 10명을 선택해 현재 매치 입력으로 불러올 수 있다.
- 저장된 플레이어를 개별 삭제할 수 있다.
- 전체 저장 플레이어 삭제 버튼이 동작한다.
- 저장된 플레이어 불러오기 영역이 옆으로 분리되어 있고, 기본 상태가 접힘이다.
- 저장된 플레이어 영역을 펼치면 각 플레이어가 한 줄 형태로 표시되어 세로 길이가 과도하게 늘어나지 않는다.
- 저장된 플레이어 한 줄의 아무 위치를 클릭해도 해당 플레이어가 선택 또는 선택 해제된다.
- 현재 10명 확인 및 선호 점수 영역에서 각 플레이어가 한 줄 형태로 표시되어 세로 길이가 과도하게 늘어나지 않는다.
- 현재 10명 확인 및 선호 점수 영역에서 이름, 티어, 선호 점수를 한눈에 빠르게 비교할 수 있다.
- 추천 팀 결과 영역의 버튼을 누르면 입력을 다시 붙여넣지 않아도 후보 조합 6개가 다시 생성된다.
- 후보 재생성 후에도 현재 입력과 선호 점수 상태는 유지된다.
- 문의 및 건의사항을 GitHub issue 로 올리라는 안내와 링크가 메인 UI 에 표시된다.
- 헤더 행이 있는 입력과 없는 입력 모두 정상 처리된다.

## Non-Goals

- 이번 라운드에서는 모바일 최적화를 필수로 요구하지 않는다.

## Definition Of Done

- 기존 단일 최적 팀 추천 기능이 유지된다.
- 후보 조합 6개 기능이 유지되고, 각 후보의 compact preview 가 빠르게 비교 가능하게 표시된다.
- 선택한 후보를 최종 편집 영역으로 불러온 뒤 클릭 기반 스왑 수정이 가능하다.
- 메인 UI 에서는 숫자 점수 노출 없이도 후보를 파악하고 수정할 수 있다.
- 역할 선호도 점수 분배, 플레이어 저장, 저장된 플레이어 중 10명 선택, 저장된 플레이어 삭제 기능이 현재 iteration 결과물에 포함된다.
- 저장된 플레이어 불러오기 UI 가 이름 중심의 단순 리스트로 정리된다.
- 저장된 플레이어 불러오기 영역이 옆으로 분리되고, 기본 접힘 상태와 한 줄 선택 UX 가 적용된다.
- 현재 10명 확인 및 선호 점수 UI 도 한 줄 중심의 조밀한 요약 레이아웃으로 정리된다.
- 추천 팀 결과 영역에서 후보 6개를 빠르게 다시 생성하는 버튼이 동작한다.
- 문의 및 건의사항용 GitHub issue 안내가 UI, README, FINAL_OUTPUT 에 반영된다.
- README 와 FINAL_OUTPUT 에 새 기능과 검증 방법이 반영된다.
